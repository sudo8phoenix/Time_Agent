# V2-H02 duration service handoff

Implemented a pure service in `backend/app/progress/duration.py`. It is integrated with the project-authorized `/durations` API and execution-history UI and does not mutate lifecycle or schedule records. The API owner can call `calculate_duration(start_endpoint, finish_endpoint, calendar=optional_reviewed_calendar)` and serialize the returned `DurationResult` as a dataclass (for example `dataclasses.asdict`). `labour_productivity(...)` deliberately always returns unavailable until compatible measured labour data and allocation rules exist.

## Result contract

`DurationResult.status` is `available` or `unavailable`; `basis` identifies `date_span`, `elapsed_clock_time`, or `elapsed_clock_time_and_reviewed_calendar`. Unavailable results carry a stable `reason`. Timed elapsed results report midpoint seconds plus a min/max range determined by endpoint precision. Inputs need either a timezone name or a normalized timezone-aware instant. Naive local wall times in a daylight-saving gap or fold are unavailable; an explicit normalized instant may disambiguate a fold when it agrees with the supplied local endpoint. Timed chronology uses normalized instants, so different local dates across timezones are valid when the finish instant follows the start instant. Date-only and mixed date/timed pairs expose only `date_span_days`; they never report precise elapsed hours. A missing endpoint or known finish-before-start returns unavailable.

Optional working time requires an explicit `ReviewedCalendar(version, timezone, shifts_by_weekday, holidays, reviewed=True)`. Its `Shift` definitions contain local start/finish times and optional breaks. Empty weekday shift tuples explicitly mean that weekday is a day off. Calculations use timezone-aware shift intersections, subtract breaks, exclude listed holidays, and return the calendar version. `calendar_working_seconds` is the midpoint; `calendar_working_min_seconds` and `calendar_working_max_seconds` carry endpoint precision uncertainty through the working-time intersection. Missing, unreviewed, unsupported, ambiguous/nonexistent local shift times, or timezone-mismatched calendars return unavailable for calendar-working duration. Callers that need to preserve elapsed output when calendar inputs are unavailable can make a separate `calculate_duration(start, finish)` call without the calendar; the endpoint integration owns combining those result bases. This definition is a service input only; no imported calendar is promoted or inferred as reviewed. Existing Cambridge calendar data remain unreviewed, and GT10 has no full local definition.

Working-calendar hours describe scheduled clock-time intersection only. They do not establish attendance, crew hours, continuous work, or productivity. The current schema has no measured crew-hour/allocation data, so metres per crew-hour remains explicitly unavailable.

## Validation

Focused coverage is in `backend/tests/unit/test_duration.py`, including elapsed and calendar-working precision bounds, cross-timezone chronology, date-only spans, missing timezone, DST gaps/folds, reviewed shifts/breaks/holidays, malformed calendars, and unavailable productivity. Run with `cd backend && pytest tests/unit/test_duration.py`.

## Integration note

The endpoint should source endpoints from the accepted lifecycle state/event evidence, retain each endpoint's precision and timezone, and include calendar metadata only after its semantic shape, timezone, exceptions, and version have been reviewed. The current service intentionally has no persistence or calendar lookup layer.
