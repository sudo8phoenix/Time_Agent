# V2 E01 handoff: audited reanalysis and recovery

Implemented explicit report reanalysis as a new child `Job` linked to the original report run. The new `POST /api/v1/projects/{project_id}/reports/{report_id}/reanalysis` route requires reviewer access, a reason, and an idempotency key. Reusing the same key returns the same run only when actor, report, project, and reason match. Reanalysis locks the report row while checking/creating the child, pins the currently active schedule, and rejects a stale base run. Ordinary report submission still reuses the single base job, including after child runs exist.

Job status and `GET /api/v1/projects/{project_id}/reports/{report_id}/runs` expose parent linkage, requesting actor, reason, schedule, state, and the supported configuration snapshot. The snapshot records execution mode, model name, and the extraction prompt version in effect when the rerun was requested. The worker honors the pinned execution mode and model; prompt changes remain code-versioned. Accepted evidence and decisions stay attached to their original observations and events. Approval locks the report before activity state, and blocks a same-source, same-effect application from another job, even when reanalysis selects a different activity. Same-run corrections and distinct start/finish events remain available.

Migration `0014_audited_reanalysis` replaces the one-job constraint with a partial unique index for the base run and adds child-run provenance. Its downgrade refuses to proceed while child runs exist. The backup manifest now records row IDs and canonical row-content SHA-256 digests for jobs, graph runs, activity states, lifecycle events, observations, proposals, audit events, conversations, conversation turns, and integration outbox rows. Restore verification checks IDs and content for a fixed table allowlist, alongside original files and existing evidence IDs.

Added integration coverage for normal submission idempotency after reanalysis, linked child creation, reanalysis-key retries and conflicts, reviewer/CSRF authorization, job/run lineage, both approval orders for repeated accepted work, and valid start-plus-finish events from the same source. A PostgreSQL parity test now runs the lifecycle fixture through both workers and confirms their persisted lifecycle effects match after normalizing source-fragment IDs. Existing regression suites cover lease expiry/replacement, stale schedule publication and approval, concurrent approvals, lifecycle corrections, graph execution/resumption, permissions, and outbox delivery.
