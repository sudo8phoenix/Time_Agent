## Implemented behavior

`process_job_with_graph(...)` creates or resumes the unique `AgentRun` for an owned job with `thread_id=str(run.id)`, a synchronous PostgreSQL saver, strict msgpack mode and synchronous durability. It never calls saver setup. Before and after every node boundary it checks shutdown, the fresh lease and the pinned active schedule; the existing independent worker heartbeat remains active and the runtime also renews through the supplied callback at boundaries.

Resume validates graph/state/framework identities, reloads report fragments and leaf activities from the current server-owned job scope, and reconstructs exact observation/candidate/model-budget provenance from the checkpoint. Evidence quotes, trusted relative dates, candidate immutable fields, keysets and counters are revalidated before any resumed tool can run. Completed extraction and selection model stages are not repeated.

Proposal persistence uses one independent transaction, the run ID as its idempotency key, and full canonical comparison when rows already exist. Partial/incompatible output fails closed. A committed domain transaction followed by an ambiguous checkpoint failure is recovered under a replacement lease by re-running only the persistence verifier and state-only finalizer; it does not duplicate observations or proposals. No graph path creates progress or approval audit rows.

Sanitized `AgentStep` and `AgentToolCall` records contain only hashes, counts, correlation IDs, mapping states, stable codes and durations. They exclude prompts, report text, quotes, endpoints, tokens, checkpoint data and arbitrary exception text. Selection prompt/model metadata is retained in the checkpoint and split into the three W-32 metadata columns.

`agent_execution_mode` accepts only `legacy|graph` and defaults to `legacy`. The worker selects exactly one runner server-side. A graph runtime that already atomically published its terminal job/run state marks its result `published` so the legacy worker wrapper does not publish twice.

Migration `0009_langgraph_checkpoints` snapshots the final checkpoint-postgres 3.1.2 schema and ledger migrations 0–9. The three indexes are created transactionally because the tables are new; package `CREATE INDEX CONCURRENTLY` statements are not run inside Alembic. Downgrade refuses populated/future-owned checkpoints or active agent runs.

Pruning requires an explicit positive age, defaults to dry-run, locks exact eligible terminal runs, retains retryable failed/stale runs, verifies terminal trace and domain counts, and deletes only exact thread IDs in one transaction (`checkpoint_writes` → `checkpoints` → `checkpoint_blobs`). It never deletes application traces, jobs, proposals, evidence, audit/progress rows or the checkpoint migration ledger.

Production setup is only:

```text
DATABASE_URL=<postgresql+psycopg URL> PYTHONPATH=backend .venv/bin/alembic upgrade head
```

Ordinary worker/API startup performs no checkpoint DDL.

## Pruning transcript summary

The test ages one completed ready-for-review run, confirms dry-run reports its exact run/thread and positive checkpoint counts without mutation, executes deletion, verifies deleted counts exactly match the preview, then verifies the `AgentRun`, observation and proposal remain while that thread has zero checkpoint rows. Retryable failed/stale runs are excluded by query policy.
