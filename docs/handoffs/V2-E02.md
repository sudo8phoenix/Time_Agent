# E02 — Label-blind capture and offline evaluation tooling

Status: label-blind capture persistence/conversion and partial offline metrics implemented and fixture-tested; **E02 evaluation tooling and live gate remain incomplete**. No real live UI-to-export evaluation or held-out accuracy claim is made.

## Delivered

- `evaluation/capture_live.py` validates and persists manually collected run artifacts, and `--predictions` converts cases to prediction JSONL without label fields. It rejects expected-label and self-reported-correctness fields recursively and refuses to overwrite existing outputs. It does not prove supplied records came from a live run.
- `evaluation/run.py` rejects expected-label fields recursively in predictions before scoring and keeps labels on the scorer side.
- `evaluation/metrics.py` provides partial event attribute alignment scoped to each case, endpoint date/time/precision and activity-link metrics, top-eight candidate recall, failure/abstention and scope counts, review-required/completed burden, format/discipline strata, macro project and micro case selection summaries, initial/corrected review-state field scoring, and observed latency summaries. Event alignment requires exact agreement on event type and every supplied nonempty discriminating event attribute. Cases without comparable event attributes are exposed as unaligned; when no comparable events exist, metric values are null with `status: unavailable`.
- Latency validation drops negative, non-finite, timezone-naive and reversed observations. Wall intervals remain explicitly wall time. If review start/end timestamps exist, review wait and submission-to-update less review wait are reported separately. Retry counts/duration are summarized only when supplied. Missing measurements stay unavailable.
- Unit fixtures cover nested label leakage, immutable capture output, JSONL conversion, case-scoped event alignment, keyless score availability, lifecycle durations, candidate cutoffs, missing/duplicate case IDs, and project/strata/outcome summaries.

## Capture format and limits

Capture JSON uses `schema_version: 1`, `mode: "live_ui_to_export"`, a `run` object with nonempty `commit`, `model_digest` and `prompt_config_sha256`, and a nonempty `cases` list. Each case has a unique `case_id`; `atomic_events` contain observed event attributes and `candidate_ids` record surfaced candidates. Event keys are not used as ground truth or alignment identities. Milestone timestamps use ISO-8601 fields such as `submitted_at`, `accepted_at`, `internal_update_at` and `external_acknowledged_at`. Initial and reviewer-corrected states are stored separately. The tool only validates and writes supplied observations; it does not automate a browser or establish that a run was live. Provenance must be independently confirmed.

Run with `python -m evaluation.capture_live observed-capture.json evaluation/results/live-capture-001.json --predictions evaluation/results/live-predictions-001.jsonl`. The converter emits observations; it cannot independently align authored report events. Score using `python -m evaluation.run predictions.jsonl labels.jsonl splits.json --split held_out --config '{...}'`. Alignment compares case-scoped observed attributes (`event_type`, dates/times, quantity, unit, scope and precision) when supplied; it is exact-match only and does not resolve semantic paraphrases or partial-field disagreement. Opaque event keys and model-reported correctness are ignored. Legacy count-only labels produce unavailable event correctness rather than fabricated zero or a correctness claim.

Submission-to-update remains wall time and includes any reviewer wait unless valid review start/end timestamps are also present. The separately named system interval is emitted only when the review duration is observed and fits inside submission-to-update. Retries likewise require explicit counts or duration fields. Format and discipline strata depend on label metadata; project weighting requires a `project_id` on labels. Missing metadata is counted as unclassified. These metric implementations do not establish that a capture is authentic or that labels are independent.

## Blocking evidence

The current D04 labels are AI-proposed/unreviewed and D05 partitions remain provisional. There is no independently reviewed/frozen unseen report set, agreed quality/latency acceptance target, or captured genuine UI-to-export run with production-like live model and connector provenance. `evaluation/capture_live.py` does not perform or attest the workflow. Accordingly this handoff records implementation, not E02 acceptance. No result should be described as independently validated, unseen, or live until those prerequisites and evidence exist.
