# W-13 handoff

Task ID: W-13 — concurrent approval and correction safety.

Changed files:

- `backend/app/api/endpoints/review.py`
- `backend/tests/integration/test_review_concurrency.py`

Implemented behaviour:

- Approval now locks the proposal row before checking revision/state.
- Idempotency is checked again after the lock, so a retried key returns the
  original committed response and does not create another event.
- A second approval against an already approved proposal returns the frozen
  `409 STALE_PROPOSAL` response.
- Existing same-project validation rejects a cross-project activity selection.
- The integration test verifies a forced transaction exception leaves proposal
  state, activity revision, and progress state unchanged.
- Correction/supersession remains supported by the existing frozen API and
  ledger fields; this task did not add a new correction endpoint.

Commands and results:

- `.venv/bin/pytest backend/tests/integration/test_review_concurrency.py -q`
  — 2 passed (run with local PostgreSQL access).
- `make test-integration` — 8 passed, 1 deprecation warning.

Evidence:

- The approval test observes one successful approval, an identical idempotent
  retry response, then a stale response for the loser and activity revision 1.
- The rollback test observes activity revision 0 and proposal state `pending`
  after the forced failure.

Limitations and unmet criteria:

- The test uses independently scoped sequential database sessions rather than
  timing-based concurrent requests; no sleep or race timing is assumed.
- No new correction endpoint was introduced because the existing revise and
  supersession contract already supplies the declared path.

Contract-change requests: none.

idempotent, cross-project, and rollback behaviours.
