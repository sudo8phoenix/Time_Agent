# Report planner evaluation captures

These directories retain separate attempts. Do not merge failed requests into a successful capture or treat diagnostic failures as quality rankings.

- The initial root directory contains configuration and cleanup from a harness ledger-query failure. Groq extraction succeeded; the old 48-row discovery request returned HTTP 413.
- `capture-02/` records the old request-size/rate-limit failures and a candidate adapter-construction `NameError`. That missing import is fixed and covered by a no-injected-model PostgreSQL integration test. This capture is not a valid quality comparison.
- `diagnostic-03/` isolates the candidate startup error without exposing credentials or exception messages.
- `byte-bounded-paced-04/` used an evaluation transport missing the production User-Agent and received HTTP 403 from Groq. It is invalid for provider credential or model-quality conclusions. The transport was corrected; subsequent calls returned 200 using the same key.
- `byte-bounded-paced-05/` is a valid independent live pair on one original expanded-dataset fragment with all 60 leaf schedule activities. V1 and v2 both selected the expected activity and quantity, reached pending review, and wrote zero ledger events. All 25 model requests succeeded. V1 used 11 Groq calls; v2 used the same number of live Groq calls plus three live Super VL planner calls. Elapsed times were 202.487 and 221.691 seconds, respectively; pacing accounted for 193.174 and 210.182 seconds. This single pair does not establish a latency or model-quality ranking.
- `seed-c01-retry-07/` separately retries the interrupted clear-match seed case. Both arms succeeded; the original failed first attempt is retained.
- `seed-controlled-06/` uses six original seed fragments with the entire 12-activity seed schedule. Groq specialist responses are captured live for v1. V2 replays them only when model, input, schema and generation settings have exactly matching payload fingerprints; its Super VL planner calls remain live. This checks orchestration parity and failure handling, not independent v2 specialist quality or comparative wall-clock latency. A failed live request remains a failure in both arms.

All data are synthetic and labels are unadjudicated. Labels are loaded only for scoring; no label fields are passed to model adapters. Exact source hashes, per-call journals, structured predictions, logical/live/replayed call counts, and cleanup records are retained where applicable. The evaluation only writes pending proposals in `progress_test`; no approval API is invoked and synthetic database records are removed afterward. Rollout settings and credentials are unchanged.
